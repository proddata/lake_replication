# Replication roadmap

The product direction is ordinary PostgreSQL tables continuously mirrored into Iceberg, including a **single PostgreSQL instance mirroring its own data**. We intend to support both journaled and direct publication. The packaged journaled pipeline is the current default; direct publication remains an opt-in prototype with a separate final-publication acknowledgement boundary.

Start with [supported direction and current boundaries](../design/direct-publication.md). Release execution lives in [release gates](release.md), security work in [the security roadmap](security.md), and proposed conversion/typed-write experiments in [the direct write-path plan](direct-write-path.md). Those proposals are not implemented interfaces.

## Next work

- [ ] Profile and reduce repeated native mutation file-metadata work on the coordinated direct runtime; retain an unchanged control and exact-row/recovery checks.
- [ ] Repeat the same 15-minute 6/8-transactions-per-second maintenance fixtures after a measured improvement. The current 8/second configuration misses its drain deadline; keep failed envelopes visible.
- [ ] Integrate direct publication with subscription configuration, generation/owner fencing, credentials, supervisor restart and status reporting. No production mode-switching API is selected yet.
- [ ] Define and qualify direct schema evolution beyond the frozen-schema prototype, including type/target guards and concurrent DDL.
- [ ] Add resumable large snapshots and safe concurrent WAL reconciliation beyond the current bounded atomic snapshot.
- [ ] Qualify resource admission for memory, temporary disk, retained WAL and object-store outages, with explicit recovery/rebuild procedures and pressure telemetry.
- [ ] Qualify contention, longer soaks, deployment-specific disk/power-loss and failover/restore behavior before promoting direct publication into release packages.
- [ ] Preserve independent journal-path regression and packaging coverage while direct/native optimizations evolve.

The existing source-push change-log transport is an optional separate experiment, not a prerequisite for local direct publication. Its detailed work and unfinished experiment-specific tasks are retained in the [historical source-push checklist](../archive/source-push-implementation-checklist.md).

## Implementation and qualification record

- [x] Qualify consistent initial copy, streamed mutations and rollback in one database.
- [x] Qualify local stop/start, shared-instance restart, nullable-column schema evolution and cleanup.
- [x] Verify explicit application-table selection prevents replication feedback.
- [x] Measure bounded single-instance CPU/memory, WAL, observed object operations and publication-latency upper bounds with fresh application-only baselines. In the 120-transaction local experiment, opt-in 1-second coalescing reduces CPU from 19.72 to 9.33 seconds and observed S3 requests from 1,442 to 942; sustained sizing remains open.
- [x] Qualify managed initial-copy interruption with concurrent writes, local streaming disconnect and replay, mirror-reader isolation, blocked publication and object-store outage in bounded fixtures. Earlier real publication backend-crash boundaries pass 27 checks; current-core runtime probes add managed recovery and contention evidence.
- [x] Add opt-in publication coalescing with bounded delay, responsive stop/restart and early flushing under journal transaction/byte pressure.
- [x] Qualify native local mirror compaction and bounded, checkpoint-safe journal cleanup followed by continued replication. Final-runtime publication crash tests (27 checks) and default logical compatibility cases (54 checks) pass.
- [x] Extend the local comparison to 1,000 paced transactions per mode with control-plane publication observation; mirrors match and application p99 remains around 8 ms in that bounded run.
- [x] Correct JSONB WAL publication and qualify supported scalar/compound-key/TOAST values under primary-key and full-row identity.
- [x] Qualify one controlled flow under explicit CPU/RAM caps (PostgreSQL 512 MiB, engine 1 GiB), with journal admission restricted to one transaction. Smaller internal query-budget attempts fail and are retained as unsupported configurations.
- [x] Map bounded transaction-shape trade-offs and add opt-in independent INSERT grouping with native target/DDL/permission fences. Guard tests (18 checks), grouped publication crash recovery (29 checks) and default logical compatibility (54 checks) pass on the final runtime; timed comparisons are recorded separately.
- [x] Qualify a bounded local WAL-retention overrun: lost history reports a critical source error without advancing checkpoints or replacing its invalidated slot; application commits continue and an explicit fresh snapshot restores streaming while preserving the previous mirror (17 checks). Deployment-specific disk and power-loss qualification remains open.
- [x] Extend grouped local mirroring to 10,000 transactions at an offered 100 transactions/second: exact 40,000 rows per table and bounded-run recovery after a 4.61-second drain. This does not establish a production capacity maximum.
- [x] Qualify actual WAL ENOSPC on a private 128-MiB filesystem: shared PostgreSQL stops, committed heaps survive, and freeing space/restarting restores exact mirroring and continued writes (12 checks).
- [x] Qualify bounded full-PGDATA ENOSPC: a failed application table extension aborts without changing committed heaps; freeing space restores exact mirroring and continued writes (12 checks).
- [x] Compare same-instance mirroring against remote logical pull with identical runtime/batching/storage, INSERT and mixed workloads, fresh volumes and reversed-order repetitions (eight fixtures, 56 checks). Total CPU is similar in these bounded runs; remote pull moves most replication CPU/memory/WAL away from the application side. See [comparison](../performance/local-pull-comparison.md).
- [x] Profile publication phases and add ordered typed DELETE key filtering. Reversed-order local comparisons show 21% lower median CPU on small mirrors and 35% with 20,000 existing rows/table; 189 packaged qualification checks and `make check` pass. See [optimization report](../performance/local-delete-filter.md).
- [x] Enforce opt-in coalescing between live-stream publications, preserve pressure and receiver-exit draining, and expose flush reasons. Counterbalanced mixed workloads use about 31% less CPU and 16% fewer mirror requests, with a higher sampled publication-delay upper bound. See [window report](../performance/local-coalescing-windows.md).
- [x] Profile UPDATE costs and add guarded convert-once handling for wide multi-row runs. Counterbalanced 48-column/32-row pipeline trials show about 10% lower median CPU; narrow paths are retained. Exact types, unchanged TOAST, schema evolution, fallback and wide crash recovery pass. See [UPDATE report](../performance/local-update-conversion.md).
- [x] Extend direct maintenance load tests to 15-minute write phases at 6 and 8 transactions/second. The 6/second run passes 25 checks with exact rows, 11 recovered deadlocks and an 11.83-second drain, but sampled p95 lag reaches 43.52 seconds. At 8/second, the last sample publishes 5,959/7,200 and the drain deadline fails despite 45 recovered deadlocks. Both reach the PostgreSQL memory boundary without OOM. See [sustained maintenance report](../performance/wal-direct-sustained-maintenance.md).
- [x] Test acquiring native target locks before direct publication writes. The opt-in child image passes 398 native checks, reduces observed 6/second CPU from 677.66 to 589.03 seconds and sampled p95 lag from 43.52 to 6.15 seconds, with zero retries. The full 8/second run still fails its drain deadline despite zero retries; release defaults remain unchanged. See [native lock experiment](../performance/wal-direct-prelock.md).

### Direct-publication qualification record

- [x] Add an opt-in, manually bootstrapped frozen-schema direct publisher, with bounded committed transactions, final-table/checkpoint atomic commit and WAL acknowledgement afterward. Ordinary and real publication-crash fixtures pass 125 checks without bulk PostgreSQL journal rows. See the [experiment](../../experiments/wal_direct/README.md).
- [x] Compare direct publication with a matched per-commit journal control and a coalesced journal reference: 12 fresh fixtures, reversed order, INSERT and mixed workloads, 82 checks. Direct reduces WAL by about 29%/11% versus the matched control, with only small descriptive CPU differences; coalesced journal remains much cheaper. See the [performance report](../performance/wal-direct-performance.md).
- [x] Add bounded direct coalescing with count/row/byte/time limits, idle flushing, fresh windows, stop/replay and grouped crash qualification (180 native checks). Matched-policy comparison passes eight fixtures/60 checks, with about 12%/11% lower CPU and 43%/11% lower generated WAL for INSERT/mixed workloads; direct makes slightly more publications/requests and retains more mixed-workload WAL. See [follow-up](../performance/wal-direct-coalescing.md).
- [x] Add bounded nonempty direct snapshot alignment without PostgreSQL row-data staging. Exported-snapshot copy, pre-export DDL fencing, concurrent changes, interrupted retry, lost response, existing-target/type guards and three real snapshot publication crashes pass 138 checks; immediate/coalesced streaming adds 104 passing regression checks. See [snapshot report](../qualification/wal-direct-snapshot.md).
- [x] Add opt-in streamed transactions with quota-controlled disposable spill, subtransaction abort, bounded atomic apply chunks and a durable replay floor for interleaved commits. Large transaction, quota, real spill ENOSPC, corruption, replay and three real publication-crash fixtures pass 79 checks; ordinary/coalesced/snapshot regressions add 134 checks. See [streamed recovery](../qualification/wal-direct-streaming.md).
- [x] Qualify direct storage outage and actual checkpoint-enforced WAL-history loss in both modes: application commits continue, unpublished WAL stays unacknowledged, exact replay recovers storage outages, and explicit fresh snapshots restore lost history while preserving old mirrors (54 checks). Production retention sizing and automatic supervision/rebuild remain open.
- [x] Measure bounded direct/journal resource limits, correct application-XID/empty-bookkeeping accounting, and add worker lifetime RSS/CPU diagnostics. Final no-swap memory trials pass five fixtures/94 checks; the 20,000-row-per-table journal fixture OOM-kills PostgreSQL at 512 MiB while direct completes. Mixed engine-budget failures and five-minute overload trials remain failed configurations; production sizing is still open. See [sizing study](../performance/wal-direct-sizing.md).
- [x] Profile publication growth with fixed batches, native query/decode counters and compaction. Repeated full file-catalog loads for UPDATE/DELETE dominate the growing cost; compaction cuts observed batch apply from 4.300 to 2.411 seconds while preserving rows/checkpoint. A tested unused-stats candidate has no useful gain. See [profile](../performance/wal-direct-publication-profile.md).
- [x] Add bounded whole-publication deadlock recovery and repeat sustained load with maintenance. The v13 qualification passes 345 native checks, including exact replay of 1,000 transactions at 4/second, one recovered deadlock and a 1.18-second final drain. The 3,000-transaction run at 10/second still fails its drain deadline despite recovering 15 deadlocks; production capacity remains open; the later prelock experiment above addresses the measured lock cycle in bounded fixtures. See [recovery report](../qualification/wal-direct-deadlock-recovery.md).

Large resumable snapshots, managed direct lifecycle and production qualification remain in the next-work list above. Bounded streamed spill and outage/history-loss recovery are already implemented and tested above.
