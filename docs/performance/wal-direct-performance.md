# WAL-backed direct publication: first performance comparison

The frozen-schema prototype reduces PostgreSQL WAL generation relative to a journal pipeline with matching one-transaction publications. It does not yet establish a substantial total CPU advantage. The existing coalesced journal pipeline remains considerably cheaper in these workloads; direct publication needs bounded batching before evaluating replacement of the journal path.

[Curated evidence](../evidence/2026-11-15-wal-direct-performance.json) records 12 successful fresh fixtures and 82 checks. Final source/mirror row hashes match in every mode and repetition. All fixtures clean up successfully. `make check` and `git diff --check` pass. The separate [125-check recovery evidence](../evidence/2026-11-15-wal-direct-prototype.json) covers the first direct-publication slice.

## Method

All modes run on local ARM64 Docker fixtures and use the exact same cached runtime image (`lake-local-iceberg:wal-direct-v3`, image `sha256:fa8365a5d08d3f853d4811669b54be289c7028c297b29dd6b2b6bbfd14b13885`), PostgreSQL/core SQL, pgduck engine and source-pinned MinIO images. Each fixture starts from fresh private volumes. No other local qualification runs compete with the timed intervals.

Each workload has 120 transactions at four offered transactions/second, with four INSERTs per table into two tables and 256-byte text values. The mixed case additionally UPDATEs one and DELETEs one prior-transaction row per table. A seed transaction warms both paths before measurement; it is excluded from timing, publication counts and object traces. Initial setup and final full-row checks are outside the resource interval.

Three modes are run twice per workload, reversing their order in the second repetition:

- **Journal per commit:** existing managed receiver/supervisor/publisher, no coalescing or INSERT regrouping. A disposable `next_batch` wrapper caps publications at one transaction; retained journal rows prove the cap was respected.
- **Direct per commit:** one persistent experimental worker, one transaction per final Iceberg publication, no bulk row-data journal.
- **Coalesced journal:** existing managed pipeline, one-second coalescing, at most 32 transactions/publication, independent INSERT grouping enabled.

The [batch-cap overlay](../../experiments/wal_direct/benchmark_batch_cap.sql) only limits selection through the original `next_batch` function. Journal admission, publication, fencing and recovery functions are unchanged. It is installed only in disposable benchmark databases.

This compares implementations, not the isolated cost of writing a journal. Direct uses a manually bootstrapped loopback superuser and protocol v1 without streaming; journal uses its managed lifecycle, unprivileged worker, generation fences, schema validation and protocol v4. Both reuse current `apply_change_run` row semantics. The direct prototype has fewer capabilities, so small CPU differences cannot establish architectural superiority.

## Database and engine cost

Values are medians of two runs. CPU is PostgreSQL plus pgduck cgroup CPU, including container observer overhead. WAL is generated by the shared PostgreSQL instance during the measurement interval. Object requests are observed requests for final mirror output, including reads and metadata work.

| Workload | Mode | CPU seconds (range) | WAL MiB | Object requests | Publications |
|---|---|---:|---:|---:|---:|
| inserts | Journal per commit | 20.15 (18.85–21.45) | 3.26 | 1,442 | 120 |
| inserts | Direct per commit | 19.40 (17.17–21.63) | 2.30 | 1,442 | 120 |
| inserts | Coalesced journal | 7.24 (6.97–7.51) | 1.89 | 300 | 25 |
| mixed | Journal per commit | 34.76 (34.52–34.99) | 14.02 | 3,108 | 120 |
| mixed | Direct per commit | 33.68 (33.47–33.88) | 12.48 | 3,108 | 120 |
| mixed | Coalesced journal | 15.75 (15.75–15.75) | 11.50 | 2,086 | 18 |

Direct reduces median WAL by 29.3% for INSERTs and 11.0% for mixed mutations versus the matching journal control. Total CPU medians are only 3.7% and 3.1% lower respectively. INSERT CPU ranges overlap; the mixed ranges differ in these two trials, but neither result establishes statistical significance or a general throughput improvement. Request counts are identical between the two per-commit modes.

The coalesced journal reference uses about 63% less CPU for INSERTs and 53% less for mixed mutations than direct per commit. It also generates less WAL than the unbatched direct path. Thus removing the journal does not substitute for reducing final-table publication frequency. The measurements do not identify one internal phase as the cause; metadata checking, worker lifecycle and final Iceberg work all remain relevant.

## Latency, memory and retained WAL

Publication delay is a p95 **observed upper bound**, including two-second sampling/query delay. Application p99 is client-observed transaction time, not server COMMIT time alone. PSS is sampled process memory across PostgreSQL/workers and pgduck; it apportions shared pages and does not establish a hard bound. Retained WAL uses the logical slot restart LSN, not just its confirmed-flush LSN.

| Workload | Mode | App p99 ms | Publication p95 upper bound s | Peak sampled PSS MiB | Peak observed retained WAL MiB |
|---|---|---:|---:|---:|---:|
| inserts | Journal per commit | 5.77 | 2.45 | 248.7 | 2.54 |
| inserts | Direct per commit | 6.14 | 2.46 | 231.5 | 1.83 |
| inserts | Coalesced journal | 8.28 | 3.40 | 203.5 | 1.24 |
| mixed | Journal per commit | 3.67 | 4.13 | 272.3 | 7.93 |
| mixed | Direct per commit | 3.67 | 3.45 | 255.1 | 10.99 |
| mixed | Coalesced journal | 9.78 | 4.07 | 243.3 | 7.23 |

Coalescing trades a higher sampled publication-delay bound for lower resource use here; application p99 is also higher in its fixtures. Direct uses less sampled PSS than the matching journal control, but INSERT ranges overlap and these workloads buffer only small transactions. This does not qualify general memory admission.

Direct retains more peak WAL in the mixed workload despite generating less WAL overall. There is no object-store outage in this comparison, and slot restart-LSN movement also depends on decoding/checkpoint history. These retained-byte observations do not establish outage capacity. Direct still needs explicit WAL budgets and invalidation/rebuild behavior for prolonged outages.

## Proposed next experiment at the time

Add bounded direct coalescing: a time window plus limits on complete transactions, rows and aggregate bytes. Preserve source order, never split a transaction for acknowledgement, commit final data and the last complete source boundary atomically, and acknowledge only afterward. Requalify grouped multi-table publication crashes, lost responses, idle-window flushing, stop/restart, memory pressure and WAL loss before comparing matched coalesced modes.

Keep the default journal path. Snapshot alignment, streamed/spilled transactions, managed lifecycle integration, lineage recovery and production sizing remain open. These two-repeat local measurements are descriptive; they do not establish saturation throughput, cold-cache behavior, statistical confidence or a production capacity maximum.
